## Findings

### Gate 2: Consistency / DRY

- **finding 1** (observation): `src/fabulexa_forge/datasets/fetch.py:127-133` (`_resolve_entry`) and `tools/build_dataset_pack.py:264-268` (inline lookup in `main`) both scan `manifest.datasets` for a name match and, on miss, build the identical message `f"unknown dataset {name!r}; valid names: {valid}"`. Same search-then-list-valid-names shape, duplicated across the runtime `get`-pipeline and the repo-side builder. Not flagged as a blocker: the two call sites deliberately use different error-handling models (`fetch.py` raises `DatasetError`, consumed by `cli.py`'s stderr/exit-1 mapping; `build_dataset_pack.py::main` prints+returns directly, and never imports `DatasetError`/`get_dataset` — a deliberate decoupling per the sprint's "repo-side, never shipped" boundary). A shared "resolve entry by name" helper would need to either raise an exception the builder doesn't otherwise use, or be refactored to return `None`+message, neither of which is an obvious net win given the small size of the duplicated block.

### Gate 4: Test Value

- **finding 1** (observation): `tests/datasets/test_models.py` — `test_non_https_url_rejected`, `test_sha256_wrong_length_rejected`, `test_sha256_uppercase_rejected`, `test_size_bytes_zero_rejected`, `test_size_bytes_negative_rejected`, `test_base_format_version_zero_rejected`, `test_empty_configs_rejected`, `test_empty_commands_rejected`, `test_configs_not_yaml_suffix_rejected`, `test_command_without_dir_placeholder_rejected`, `test_command_with_foreign_placeholder_rejected` are 9 tests whose bodies differ only in which `_entry(...)` kwarg is overridden and the literal bad value — `@pytest.mark.parametrize` (as already used two paragraphs above for the name and configs-path-separator cases) would cover the same enumerated list with one test function. Each test does correctly pin a distinct validation rule (only one field is broken per test, all others valid, so `pytest.raises(ValidationError)` is not vacuous) — this is multiplication, not a weak-assertion problem. See Gate 7c: the spec itself (`spec.md` Phase 1 Tests) enumerates "Refusals, one test each," so this shape was spec-directed.
- Related, lower-severity: `tests/datasets/test_get_dataset.py`'s `test_unsafe_absolute_path_member`, `test_unsafe_traversal_member`, `test_unsafe_symlink_member`, `test_unsafe_fifo_member` share ~90% line overlap (build one unsafe `TarInfo`, call `get_dataset`, assert the same three postconditions) but differ enough in `TarInfo` construction (symlink needs `linkname`, fifo needs `.type`) that full parametrization is less clean; recorded for completeness, not a strong candidate.

### Gate 5: Coverage

- **finding 1** (observation): `src/fabulexa_forge/datasets/manifest.py:69` — `render_dataset_listing`'s `raise ValueError(f"unknown listing format: {fmt!r}")` (a documented `Raises:` clause in the spec contract) has zero test coverage. The CLI never reaches it because argparse's `choices=("text","json")` guards the only production call site, but the function is public library surface (re-exported from `datasets/__init__.py`) whose own contract promises this raise.
- **finding 2** (observation): `src/fabulexa_forge/datasets/fetch.py:219` — `_prepare_target`'s `target_dir.unlink()` branch (force-replacing an occupied *non-directory* target) is untested. `test_occupied_target_with_force_removed_and_recreated` only covers the directory-replacement branch; `test_occupied_non_directory_target_without_force_refuses` covers the non-directory case only *without* `--force`. The `force=True` + non-directory-target combination that spec's Phase 2 "Occupied target with `force=True`" bullet describes generically is not tested for the non-directory sub-case.
- Minor: `manifest.py:104` (`_human_size`'s sub-1024-byte "B" branch) is also untested — both fixture entries in `test_manifest.py` are KB/MB-scale.

### Gate 7: Spec ↔ Codebase

- **finding 1** (observation, 7b): `tools/build_dataset_pack.py`'s `build_pack` docstring (matching `spec.md:192-195`) states normalization includes "mode 0644 for files, **0755 for directories**." The implementation (`_member_tarinfo`, `_write_deterministic_archive`) never creates an explicit tar directory member — `bundle/run.duckdb` etc. rely on tarfile/extraction's implicit parent-directory creation — so the 0755-directory-mode clause in both the spec and the docstring describes a code path that does not exist. Not a functional bug (extraction still works, confirmed by `test_build_success_archive_contents_exact`), but the contract text promises a normalization that is currently unreachable.
- **finding 2** (observation, 7c): The Gate 4 test-multiplication finding traces to `spec.md`'s Phase 1 Tests section, which explicitly directs "Refusals, one test each" for 11+ distinct validator rules. A single `@pytest.mark.parametrize` covering the same enumerated rule list (as the spec's own adjacent bullets do for name and configs-path variants) would have satisfied the same coverage with far less duplication — worth calibrating in the next spec pass rather than fixing in this sprint's code.
