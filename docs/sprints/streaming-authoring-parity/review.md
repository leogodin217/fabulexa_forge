## Findings

### Gate 2 — Consistency / DRY (observations)

1. `src/fabulexa_forge/exporters/streaming/selection.py:60-146` (`_resolve_stream_where`) vs `src/fabulexa_forge/exporters/source/plan.py` (`_resolve_where_selection`) — near-duplicate ~50-line gate walk.
   Both the module docstring and the sprint notes (Phase 4: "the ~50-line mirror is deliberate ... to keep streaming gate wording/errors independent") document this as an intentional non-abstraction. Applied the scope test: this is implementation-internal control flow, not an author-configurable value, so it is not a config-boundary issue; and per CLAUDE.md's Over-Engineering guidance the alternative (a parametrized shared resolver entangling `key_form`/label/error selection) would be the worse abstraction. Noted, not a required fix.

2. `src/fabulexa_forge/exporters/streaming/selection.py:182-206` (`_stream_populations`) duplicates the flat/sub-typed resolution shape of `exporters.populations.resolve_populations` rather than calling it.
   Documented in sprint notes (Phase 4: "builds Population tuples directly rather than via resolve_populations, avoiding Source*-named errors leaking into streaming"). Verified `resolve_populations` does raise `SourceTableKindUnknown`/`SourceTableSubTypeUnknown`/`SourceSubTypesOnFlatKind` — inappropriate error identities for a streaming caller whose own gates already validated existence/domain membership earlier in `_validate_kind_stream`/`_validate_membership_stream`. Reasonable, documented tradeoff — not flagged as a violation.

### Gate 5 — Coverage (observations)

3. `src/fabulexa_forge/exporters/streaming/engine.py:418-431` (`_validate_membership_stream`'s owner `sub_types` gates) — the two new `ExportError` raises ("owner kind '{kind}' is not sub-typed; sub_types is not addressable" at line 421, and "sub_type '{value}' is not declared for owner kind '{kind}'" at line 428) have **zero test coverage**. Searched all of `tests/` for both message fragments — no hits. These are genuinely new Phase 4 validation paths (the docstring of `_validate_membership_stream` explicitly documents them as new raises) that the spec's Contract section calls out but the Phase 4 test list doesn't explicitly enumerate. Low risk (structurally simple guard clauses, and the analogous kind-stream gates at engine.py:361/369 are tested), but a genuine coverage gap in new sprint code.

4. `src/fabulexa_forge/exporters/streaming/presentation.py:248` (`_stream_subject_kind`'s membership branch, `return stream.membership.kind`) — uncovered. Confirmed no test in `tests/exporters/streaming/` constructs a `MembershipStream(..., kind_label=...)`, so `resolve_stream_kind_vocabulary`'s per-stream masquerade-check loop never exercises a membership-shaped stream's `kind_label`. All of `test_presentation.py`'s vocabulary/masquerade tests (`TestKindVocabulary`, lines ~490-587) use only `KindStream`. The one `MembershipStream` presentation test (`test_membership_value_schema_fields_equal_event_plus_resolver_output_keys`, line 692) calls `_build_value_schemas` directly and declares no `kind_label`, so it never reaches this branch either.

5. `src/fabulexa_forge/exporters/streaming/engine.py:934-935` (`_validate_stream_naming`'s except-wrap: `raise type(exc)(f"stream '{stream.name}': {exc}") from exc`) — uncovered. Both `StreamRenameUnresolvable` and `StreamOutputNameCollision` are exercised only by calling `resolve_stream_output_columns`/`resolve_membership_output_columns` directly in `test_presentation.py` (lines 300, 430 and others), which raise the *unwrapped* message. No test drives a rename/collision failure through `iter_stream_events` itself, so the "message leads with the stream name" behavior promised by `iter_stream_events`'s own docstring/raises-clause (spec § Contracts, engine deltas) is unverified end-to-end.

   Related, same neighborhood: `selection.py:204` (`_stream_populations`'s flat-kind branch) and `selection.py:282` (`resolve_stream_selection`'s `spine_sql is None` early-return) are also uncovered — both are reachable only via a `where`-bearing selection over a *flat* kind, or a `sub_types` declaration that (redundantly) names the full domain with no `where`; no test in `test_selection.py` constructs either scenario (its shared fixture kind, `gizmo`, is always sub-typed).
